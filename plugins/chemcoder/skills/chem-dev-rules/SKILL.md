# 上位机开发 Agent 行为规范

> 本技能是 AI 编程助手（Claude Code / GitHub Copilot Chat / 同类 Agent）在上位机仓库执行开发任务时的**强制行为准则**，尤其适用于**多 Agent 协作编程**场景。所有生成的代码、提交、分支操作、文档产出必须符合本规范。来源：上位机知识库《1.1 C#语言编程规范》《1.2 开发流程管理说明》《2.1 代码版本管理总则》《2.2 版本分支管理规范》《2.3 版本发布流程说明》，叠加团队多 Agent 协作补充约定。配套的审查规范见 `chem-code-review` 技能。

---

## 0. 项目上下文

- 语言：**C# / .NET**，中控上位机系统（Chemlex 系列）。
- 分层：流程编排（工艺步骤/状态机/任务队列/批次调度）、设备驱动与通信（PLC/总线/仪器/传感器）、HMI（监控/操作/报警）、对外集成（HTTP API/MQ/LIMS/MES）、配置与报警、异常与日志。
- 领域属性：**工业控制软件**，涉及设备动作、安全联锁、物理流程。任何可能改变设备行为、报警逻辑、联锁条件的改动，必须按 A 类变更对待。
- 协作模式：**多 Agent 并行开发**，同一仓库可能同时有 Claude、Copilot、其他模型或人类工程师在不同模块上工作。

## 1. 多 Agent 协作规范（协作场景必读）

### 1.1 角色与模块边界

- 每个 Agent 只在被明确分配的**模块 / 命名空间 / 分支**内工作，不跨模块"顺手优化"别人的代码。
- 模块边界由命名空间体现：`Chemlex.<Product>.<Module>.<Submodule>`。改动不属于自己模块的文件时，必须在 MR 描述中显式说明原因，并 @ 对应模块负责人。
- 公共契约（接口、DTO、枚举、事件）被多个模块共享，修改前必须先在交接文档/MR 描述中通知所有消费方 Agent。

### 1.2 上下文交接规范（不同模型 Agent 之间必须遵守）

当一个 Agent 完成一个阶段、任务被移交给下一个 Agent（或人）时，**交接消息必须包含以下六段，缺一不可**：

| 段落 | 内容要求 |
|---|---|
| **① 已完成** | 改了哪些文件、实现了什么、commit hash、当前分支名 |
| **② 当前状态** | 是否编译通过、单元测试结果、联调状态、当前是否可运行 |
| **③ 待办** | 下一步具体要做什么，拆成可执行的小步骤 |
| **④ 已知坑** | 配置项、驱动版本、设备行为、时序陷阱、已踩过的坑 |
| **⑤ 接口契约** | 本模块对外暴露的类 / 方法签名、入参出参、可能抛的异常；**如本次改动了接口签名，必须显式列出" breaking change 清单"** |
| **⑥ 未解决问题** | 明确列出遗留疑问、阻塞点、需要人类决策的事项——**不要让下一个 Agent 猜** |

**禁止**的交接方式：
- ❌ "已经改好了，你继续吧"（信息不足以接手）
- ❌ 只说"修了个 bug"不说根因和影响范围
- ❌ 把半编译通过、半测试通过的中间态扔给下一个 Agent 而不标注

### 1.3 接口先行

- 跨模块协作时，**先定义接口（`IXXXService`）和数据契约（DTO / record），再并行实现**。
- Agent A 修改了公共接口签名，必须在 MR 描述中显式列出"影响的下游调用方"，并在交接消息 §⑤ 中标红。
- 禁止偷偷改公共接口签名而不通知协作方——这会导致其他 Agent 本地编译失败且不知道原因。

### 1.4 合并冲突责任

- 谁后合并谁解决冲突。
- 解决冲突时**必须理解双方业务意图**，不能只取一边、不能 `git checkout --theirs` 了事。
- 冲突解决后必须重新跑：编译 + 受影响模块的单元测试。

### 1.5 模型差异抹平

- 不同模型（Claude / Copilot / 其他）代码风格可能不一致，**最终以本规范 §2 为准**。
- Agent 提交前自检：不要留下自己的"模型风格痕迹"——例如：
  - 不要留大段解释性注释（如 `// Below is the method that does X`）
  - 不要留没用的 `using`、没用的 `var` 推导
  - 不要把简单逻辑写成过度设计的多层抽象
- 合并前跑一次 `.editorconfig` 格式化，保证全仓库风格一致。

## 2. 编码规范（生成代码时必须遵守）

### 2.1 命名（强制）

| 元素 | 规则 | 示例 |
|---|---|---|
| 命名空间 | `公司名.产品名.模块名.子模块名`；避免与 .NET 命名空间冲突 | `Chemlex.ERP.OrderManagement.Services` |
| 类 / 记录 | PascalCase，名词或名词短语；派生类体现基类关系 | `CustomerService`、`OrderProcessException` |
| 接口 | 大写 `I` 开头 + PascalCase | `IRepository<T>`、`ICustomerService` |
| 方法 | PascalCase，动词短语；布尔方法以 `Is/Has/Can` 开头 | `GetCustomerById()`、`IsValidEmail()` |
| 属性 | PascalCase，名词/形容词；布尔属性用 `Is/Has/Can` 前缀 | `IsActive`、`MaxRetryCount` |
| 私有字段 | 下划线开头 + camelCase；尽量 `readonly` | `_logger`、`_retryCount` |
| 常量 | PascalCase | `MaxRetryCount`、`DefaultCurrency` |
| 参数 / 局部变量 | camelCase | `orderId`、`customerName` |
| 泛型参数 | 单个用 `T`；多个用 `T` 开头描述名 | `TEntity`、`TKey` |

**禁止**：单字母变量（除循环计数器 `i/j`）、拼音命名、与 .NET 框架冲突的命名空间。

### 2.2 格式（强制）

- 缩进：**4 个空格，禁止 Tab**。
- 大括号：**Allman 风格，单独占一行**；即使单行语句也必须带大括号，禁止省略。
- 空格：运算符两侧、关键字后（`if (`、`while (`）、逗号后必须加空格；方法名与左括号之间、括号内侧不加空格。
- 行宽：**≤ 120 字符**；超长在运算符前或参数列表处换行。
- 每行只声明一个变量；声明尽量靠近使用处。
- 方法之间、类成员逻辑分组之间、字段与首个方法之间加空行。

### 2.3 注释规范（强制，团队统一格式）

**统一注释签名格式：`// 【内容】--【开发人】/【YYYY-MM-DD】`**

开发人写人名缩写（与分支命名一致），日期用 ISO 短格式。

#### 2.3.1 类级注释（每个类必须有）

每个类必须有 XML 文档注释，**标注所属业务模块 + 类职责**，并在类上方用团队格式列出关键修改历史：

```csharp
/// <summary>
/// 订单处理服务 —— 属于「订单管理」模块
/// 负责订单创建、校验、提交、取消全流程；是订单模块对外的门面
/// </summary>
// 【初版：订单创建 + 基础校验】--【张三】/【2026-11-04】
// 【新增：大额订单人工审批分支】--【李四】/【2026-11-10】
// 【修复：并发扣库存超卖问题】--【张三】/【2026-11-15】
public class OrderService
{
    // ...
}
```

#### 2.3.2 方法级注释（每个 public / protected 方法必须有）

必须用 XML 文档注释**详解方法功能**，不能只写方法名复述：

```csharp
/// <summary>
/// 创建订单并落库。先校验客户状态与库存，再按价格规则计算金额，
/// 金额超过阈值时触发人工审批，审批通过后才生成正式订单号
/// </summary>
/// <param name="request">创建订单请求，含客户ID、商品列表、收货地址</param>
/// <returns>新建的订单实体，含生成的订单号与初始状态(待审批/待支付)</returns>
/// <exception cref="ArgumentNullException">request 为 null 时抛出</exception>
/// <exception cref="InvalidOperationException">客户已冻结或库存不足时抛出</exception>
public async Task<Order> CreateAsync(CreateOrderRequest request)
{
    // ...
}
```

- private 方法：如果逻辑不直观（工艺规则、设备时序、报警映射），必须写注释；纯 get/set 之类省略不写。
- 方法注释要写**业务意图**，不要复述代码（反例：`// 循环遍历订单列表`）。

#### 2.3.3 关键代码行内注释

以下位置必须加行内注释，解释"为什么这么做"而不是"做了什么"：

- **业务规则阈值**（如金额审批阈值、超时时间、重试次数）
- **设备动作 / 联锁 / 急停相关逻辑**
- **报警映射 / 状态机迁移分支**
- **非显而易见的算法或 workaround**
- **对接外部系统的时序假设**

格式：
```csharp
// 【大额订单必须走人工审批，阈值从 AppSettings 读取】--【张三】/【2026-11-04】
if (request.Amount > ApprovalThreshold)
{
    await SendApprovalAsync(request);
}

// 【PLC 写入后必须等 200ms 再读回，否则读到旧值——现场调试确认】--【杨工】/【2026-09-20】
plc.Write(addr, value);
await Task.Delay(200);
```

#### 2.3.4 注释标记

待办 / 临时方案统一用：`TODO` / `HACK` / `FIXME` / `NOTE` / `OPTIMIZE`，注释符后留一个空格。不保留被注释掉的死代码。

### 2.4 编码实践（强制）

#### 2.4.1 基础实践

- **禁止魔法值**：任何业务数字/字符串字面量必须提炼为 `const` 或 `enum`。
- 字符串拼接优先 `$"..."`；循环内大量拼接用 `StringBuilder`。
- 字符串比较显式指定 `StringComparison`；空串判断用 `string.IsNullOrWhiteSpace`。
- 集合返回 **空集合（`Enumerable.Empty<T>()` 或空 List），禁止返回 `null`**。
- 空值处理：优先 `?.` 和 `??`；public API 入参必须做空值校验。
- 嵌套层级 ≤ 3 层；超过时用**卫语句（guard clause）提前 return/throw** 展开。
- 方法单一职责；**方法参数 ≤ 5 个**，超过则封装为 Request/Options 对象。
- 所有 `IDisposable` 对象必须用 `using`。
- 异步方法命名以 `Async` 结尾；**禁止 `async void`**（事件处理器除外）；库代码用 `ConfigureAwait(false)`。
- LINQ 多次枚举先 `.ToList()` 物化；存在性判断用 `.Any()` 而非 `.Count() > 0`。

#### 2.4.2 避免过度防御（强制）

多 Agent 协作中最容易出现的毛病就是"为了不出错到处加判断"，导致代码冗长、可读性差、掩盖真实 bug。**必须避免**：

- ❌ 对**内部可信调用方**（private 方法、同程序集 internal 方法）重复做参数 null 校验——public 入口校验一次即可，内部信任契约。
- ❌ 对不可能发生的分支写 `try-catch` 后吞掉或记录日志——让异常自然炸出来。
- ❌ 写 `if (x != null && x.Y != null && x.Y.Z != null)` 这种嵌套防御链——直接用 `?.` 表达，或在前置卫语句中处理。
- ❌ 为"保险"加一堆冗余的 `if (config == null) config = Default;`——启动时就该保证配置加载成功。
- ❌ 同一个参数在每个方法里都校验一遍——在入口校验一次，下游信任。
- ✅ 该校验的地方（public API、外部输入、设备返回数据、跨进程数据）必须校验；不该校验的地方别加。
- 判断标准：**这段防御是在防御"调用方用错"，还是在防御"自己写错"？** 前者保留，后者删掉。

#### 2.4.3 避免内部匿名类和匿名方法（强制）

工业上位机代码需要长期维护、被多个 Agent 反复阅读，**过度匿名会让代码难以跳转、难以测试、难以在 MR 中讨论**：

- ❌ 不要用 `delegate { ... }` 匿名委托，优先具名方法。
- ❌ 事件订阅不要用匿名 lambda：`foo.OnEvent += (s, e) => DoSomething();`——这样**无法取消订阅**，会导致内存泄漏；必须用具名方法 `foo.OnEvent += Foo_OnEvent;`。
- ❌ 不要把业务逻辑写在超过 5 行的 lambda 里——复杂逻辑抽成 `private` 具名方法，便于注释和测试。
- ❌ 匿名类型（`new { ... }`）**只允许**在 LINQ `Select` 临时投影、一次性局部变量中使用；**禁止**用匿名类型作为方法返回值、跨方法传递的数据载体——跨方法用 `record` 或具名 `class`。
- ✅ LINQ 简单链式查询（`Where/Select/OrderBy/ToList`）可以保留 lambda；一旦 lambda 里出现多行逻辑、变量声明、业务判断，就抽方法。

### 2.5 异常处理（强制）

- **禁止 `catch (Exception)` 泛型捕获**——只 catch 你能处理的具体异常类型。
- **禁止空 catch 块**（吞异常）。
- 无法处理的异常用 `throw;` 原样重抛，禁止 `throw ex;` 重置堆栈。
- 抛出语义化异常：参数空 `ArgumentNullException`、参数越界 `ArgumentOutOfRangeException`、状态非法 `InvalidOperationException`。
- 业务领域错误定义自定义异常类（继承 `Exception`，带业务属性如 `OrderNumber`）。

### 2.6 安全（强制）

- **所有外部输入必须校验**（非空、长度、范围、格式）。
- **禁止字符串拼接 SQL**；必须用参数化查询或 ORM（EF Core / Dapper 参数）。
- 密码必须用 PBKDF2/bcrypt/Argon2 加盐哈希存储，**禁止明文或可逆加密**。
- **禁止在代码中硬编码密钥、连接字符串、API Key**——从 `IConfiguration` / User Secrets / 密钥管理服务读取。
- **禁止把密码、令牌、个人信息写入日志**。

### 2.7 单元测试（新功能必须覆盖）

- 测试方法命名：`MethodName_Scenario_ExpectedBehavior`，例如 `GetCustomer_WithNegativeId_ThrowsArgumentException`。
- 结构遵循 **AAA**（Arrange / Act / Assert）。
- 必须覆盖：正常路径、边界条件（0 / 空 / 极值）、异常路径（null / 非法入参）。
- 用 Moq 隔离依赖；异步测试用 `async Task`。
- 测试数据用 Builder 模式构造。
- 测试方法本身也是方法，**遵循 §2.3.2 的注释要求**（复杂测试场景要写注释说明这个用例在验证什么业务规则）。

## 3. Git 分支与提交规范（强制）

### 3.1 分支模型

| 分支 | 用途 | 可否直推 |
|---|---|---|
| `master` | 生产已发布稳定代码（保护分支） | **禁止** |
| `development`（或称 `dev`） | 主开发分支（保护分支） | **禁止** |
| `devtest/yyMMdd-测试功能概述` | 集成测试集成分支（周期性重建） | 经 MR |
| `feature/yyMMdd-功能简述-姓名缩写` | 新功能开发 | 个人分支可直接提交 |
| `bugfix/yyMMdd-修复简述-姓名缩写` | 生产 Bug 修复 | 个人分支可直接提交 |
| `test/yyMMdd-测试概述-姓名缩写` | 纯测试验证分支 | 个人分支可直接提交 |

- 命名中的 `yyMMdd` 是**创建当天日期**，`姓名缩写` 是开发者（或 Agent 标识）。
- `master`、`development` **永不删除**；`feature/*`、`bugfix/*`、`test/*` **合并后必须删除**；`devtest/*` 周期性重建。

### 3.2 工作流（Agent 必须遵循）

1. **开新任务前**：从最新 `development` 切出 `feature/yyMMdd-描述-你` 或 `bugfix/yyMMdd-描述-你`。
2. **开发中**：在个人分支提交，commit message 见 §3.3。
3. **自测完成后**：提交 MR 到 `devtest/yyMMdd-xxx`。
4. **代码评审**：至少 1 人（或协作 Agent）Review 通过后合入 devtest。
5. **测试通过后**：**先 `git pull origin development` 并本地合并解决冲突，确认无问题后**，再提 MR 到 `development`。
6. **合入 development 后**：删除个人 feature/bugfix 分支。
7. **紧急热修**：可从 `feature/*` 或 `bugfix/*` 直接 MR 到 `development`（跳过 devtest），MR 描述说明原因。

### 3.3 Commit 与 MR 规范

- Commit message 祈使句、首字母大写、主题行 ≤ 50 字符；多文件逻辑改动正文说明动机。
- MR 标题：`[类型] 简述`，类型取 `feature` / `bugfix` / `refactor` / `docs` / `test` / `chore`。
- MR 描述必须包含：
  - 改动目的
  - **影响模块 / 影响的下游 Agent 或调用方**（多 Agent 协作必填）
  - 自测结果
  - 关联需求编号
  - **是否破坏公共接口签名**（如是，列出 breaking change 清单）
- **禁止向 `master`、`development` 直接 push**——必须通过 MR，至少 1 名非作者 Review 通过。

## 4. 发版规范（强制）

### 4.1 双轨发版

| 场景 | 分支 | tag 形式 | 说明 |
|---|---|---|---|
| 日常试运行 / 集成验证 | `dev` | `vX.Y.Z-rc.N`（如 `v1.3.0-rc.1`） | **不等于正式发版** |
| 正式归档发版 | `master`（由 `dev` 合并而来） | `vX.Y.Z`（无后缀，如 `v1.3.0`） | 正式对外版本 |

- **dev 上的 tag 不能代替正式发版**。正式发版必须：`dev → master` 合并且在 `master` 打无后缀 tag。

### 4.2 版本号（语义化）

`主.次.修订`（`x.y.z`）：
- **x 主版本**：不兼容接口/行为变更、重大架构调整。
- **y 次版本**：向下兼容的新功能。
- **z 修订号**：向下兼容的 Bug 修复。
- 预发布后缀统一 `-rc.N`（同项目内保持一致）。
- tag 前缀统一小写 `v`；**同一 `x.y.z` 正式 tag 只打一次**，重发必须递增修订号。

### 4.3 发版前自检清单

日常发版（dev）：
- [ ] 目标 commit 已在 dev 上，自测通过
- [ ] 工程内版本号（.csproj / 程序集版本）已更新为 `X.Y.Z-rc.N`
- [ ] 构建成功，制品可运行
- [ ] 在 dev 打 annotated tag 并 push
- [ ] 登记：tag 名、commit hash、制品位置、已知问题

## 5. 开发流程门控

接到开发任务后，**先判定变更等级**，再决定产出哪些文档、走哪些步骤。

| 等级 | 典型场景 | Agent 必须产出 |
|---|---|---|
| **A 类 重大** | 新工艺步骤、新设备接入、流程重构、安全联锁变更 | 需求说明 + 设计说明 + 开发记录 + 联调记录 + 测试计划 + 测试用例 + 测试记录 + 发布说明 + 上线配置清单；**设计评审必须开** |
| **B 类 中等** | 接口变更、设备/报警配置修改、队列逻辑调整 | 设计说明 + 联调记录（涉及设备/接口时）+ 测试计划 + 用例 + 记录 + 发布说明 |
| **C 类 小改** | Bug 修复、日志优化、HMI 文案调整 | 测试记录 + 发布说明 |
| **D 类 trivial** | 注释、格式、无行为变更 | 无强制文档 |

### 5.1 文档存放

```
docs/features/FEAT-YYYYMMDD-简短描述/
├── 需求说明.md
├── 设计说明.md
├── 联调记录.md
├── 测试计划.md
├── 测试用例.md
├── 测试记录.md
└── ...
docs/releases/RELEASE-v主.次.修订.md   # 可选
```

### 5.2 开发阶段 Agent 自检（必做）

- [ ] 编译通过、无 warning 被静默吞掉
- [ ] 配置变更与代码改动同步提交
- [ ] 关键路径有日志；异常路径有报警映射
- [ ] 仿真/Mock 模式下主流程可跑通（如适用）
- [ ] 新增 public 类/方法有完整 XML 注释（§2.3）
- [ ] 关键业务代码有 `【内容】--【开发人】/【日期】` 行内注释
- [ ] 没有过度防御、没有过长匿名 lambda、事件订阅已用具名方法
- [ ] 新逻辑有对应单元测试
- [ ] 如改动了公共接口，已在交接文档 §⑤ 列出 breaking change

## 6. 硬性禁令（TL;DR）

1. ❌ 不直接 `git push` 到 `master` 或 `development`。
2. ❌ 不在保护分支上跳过 MR / 跳过 Review。
3. ❌ 不在 `master` 上打带 `-rc` 后缀的 tag。
4. ❌ 不返回 `null` 表示空集合。
5. ❌ 不写空 `catch`、不 `catch (Exception)` 后吞掉。
6. ❌ 不在代码里硬编码密钥、连接串、密码。
7. ❌ 不用字符串拼接 SQL。
8. ❌ 不省略大括号、不使用 Tab 缩进。
9. ❌ 不对设备动作 / 安全联锁 / 报警映射做未评审的"顺手优化"——这类改动一律按 A 类处理。
10. ❌ 不在没读完现有代码、没跑通编译的情况下就声明"完成"。
11. ❌ **不在没有按 §1.2 六段式交接的情况下，把任务丢给下一个 Agent**。
12. ❌ **不偷偷改公共接口签名而不通知下游 Agent**。
13. ❌ **不对内部可信调用方重复做参数校验**（过度防御）。
14. ❌ **不写超过 5 行的匿名 lambda、不用匿名类型跨方法传数据、不用匿名方法订阅事件**。
15. ❌ **不给类/方法/关键代码留"裸代码"不加注释**——§2.3 的注释是强制的。

## 7. 输出风格约定

- 提交 MR / 写发布说明 / 做 Agent 交接时，使用简体中文，技术术语保留英文原文。
- 描述 Bug 修复时写清：现象 → 根因 → 修复方式 → 影响范围 → 回滚方式。
- 涉及设备行为的改动，必须显式说明"对现场物理设备/联锁/急停的影响"。
- Agent 交接消息严格按 §1.2 的六段式结构输出。
