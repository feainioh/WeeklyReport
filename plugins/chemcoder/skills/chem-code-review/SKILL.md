# 上位机代码 Reviewer 规范

> 本技能是 Code Review Agent（或人类 Reviewer）审阅上位机仓库 MR/PR 时的**强制工作规范**，与 `chem-dev-rules` 技能（原 AGENT_DEV_RULES.md，下文简称 **AGENT**）配套使用。Reviewer 的职责是对照该规范逐条核验，输出结构化审查意见，**不是**替作者写代码、也不是评判业务对错。文中「AGENT §x.x」均指 chem-dev-rules 技能中的对应章节。

---

## 0. Reviewer 角色与判定原则

### 0.1 你审什么、不审什么

| 审 | 不审 |
|---|---|
| 代码是否符合工程规范（命名/格式/注释/异常/安全） | 业务逻辑本身对不对（归测试和需求评审） |
| 是否遵守 Git 分支/提交流程 | 作者的个人品味 |
| 是否破坏公共接口契约、影响下游 Agent | 变量名是否"你更喜欢哪个" |
| 是否有安全/设备/联锁风险 | 重构可以怎么"更好"（除非当前写法有 bug） |
| 注释是否完整、可读、准确 | 注释长度是否符合你的审美 |
| 多 Agent 交接是否完整 | — |

### 0.2 严重级别定义

| 级别 | 含义 | 是否阻塞合并 |
|---|---|---|
| **Blocker (B)** | 安全事故、数据丢失、设备/联锁风险、违反流程红线、破坏公共契约未通知 | **必须修，否则 Request Changes** |
| **Major (M)** | 违反强制编码规范、缺关键注释、缺测试、明显可维护性问题 | 应该修；作者合理说明后可放行并建 TODO |
| **Minor (m)** | 推荐性规范未遵守、可读性改进点 | 建议修，不阻塞 |
| **Nit (N)** | 吹毛求疵、风格偏好 | 提一下即可，不阻塞，不要反复纠缠 |

### 0.3 Reviewer 输出格式

每条评论必须包含四要素：
1. **位置**：文件路径 + 行号
2. **级别**：`[B]` / `[M]` / `[m]` / `[N]`
3. **问题**：违反了哪条规范（引用 AGENT 章节号）
4. **建议**：具体怎么改（给一个正例片段）

末尾必须给一个**总结块**：
```
Review 结论：Approve / Request Changes
Blocker: 0 条
Major:   2 条
Minor:   3 条
Nit:     1 条
风险提示：无 / 有（说明）
```

## 1. Review 前置动作（开审前必做）

- [ ] 读 MR 描述：是否写了改动目的、影响模块、自测结果、需求编号？
- [ ] 确认变更等级（A/B/C/D），判断该 MR 是否带了对应等级要求的文档（见 AGENT §5 流程门控）。
- [ ] 确认分支命名是否符合 `feature/yyMMdd-描述-人名` / `bugfix/...` 格式。
- [ ] 确认 MR 目标分支正确（个人 feature → devtest；devtest 测试通过后 → development）。
- [ ] 看 CI / 构建是否绿；构建红的直接打回，不往下审。
- [ ] 若 MR 改了**公共接口 / DTO / 事件签名**，重点查本规范 §3.2 的 breaking change 清单。

## 2. 检查清单（按严重级别）

### 2.1 Blocker（B）—— 发现即 Request Changes

| # | 检查项 | 判定标准 | 对应条款 |
|---|---|---|---|
| B1 | 直推保护分支 | MR 目标是 master/development 却绕过 devtest（非热修场景） | AGENT §3.1/§3.2 |
| B2 | SQL 注入风险 | 出现字符串拼接 SQL、`$"SELECT ... {var}"` 形态 | AGENT §2.6 |
| B3 | 硬编码密钥/密码/连接串 | 代码里出现 `ApiKey = "sk-..."`、`Password = "..."` 字面量 | AGENT §2.6 |
| B4 | 日志泄露敏感信息 | 日志里打印密码、token、完整身份证/手机号 | AGENT §2.6 |
| B5 | 吞异常 | 空 `catch { }`、`catch (Exception) { }` 后既不重抛也不处理、catch 后返回默认值掩盖错误 | AGENT §2.5 |
| B6 | 设备/联锁/急停改动未按 A 类流程 | MR 改了 PLC 写入、联锁逻辑、报警阈值、急停行为，但 MR 描述没有"对设备/现场影响说明" | AGENT §0 / §5 |
| B7 | 偷偷改公共接口签名 | 修改了 public 接口/抽象类签名、删除/改参/改返回值，但 MR 描述**没有列 breaking change 清单** | AGENT §1.3 / §3.3 |
| B8 | 返回 null 表示空集合 | public 方法返回 `List<T>`/`IEnumerable<T>` 时可能返回 null | AGENT §2.4.1 |
| B9 | 密码明文存储/比较 | 出现 `if (password == input)` 或 MD5/SHA1 存密码 | AGENT §2.6 |
| B10 | 未授权跨模块改动 | 改动了非本 Agent 负责模块的文件，且 MR 描述未说明原因、未 @ 模块负责人 | AGENT §1.1 |

### 2.2 Major（M）—— 应当修复

| # | 检查项 | 判定标准 | 对应条款 |
|---|---|---|---|
| M1 | 命名违规 | 类名/方法名非 PascalCase、接口未以 I 开头、私有字段未下划线开头、变量用拼音或单字母（循环计数除外） | AGENT §2.1 |
| M2 | 大括号风格错误 | 大括号不单独占行（K&R 风格）、单行语句省略大括号 | AGENT §2.2 |
| M3 | Tab 缩进 | 文件里出现 Tab 字符做缩进 | AGENT §2.2 |
| M4 | 行宽超限 | 单行超过 120 字符（合理例外如长字符串、URL 可放过） | AGENT §2.2 |
| M5 | 类缺 XML 注释 | public 类没有 `/// <summary>`，或 summary 没写所属业务模块+职责 | AGENT §2.3.1 |
| M6 | 方法缺 XML 注释 | public/protected 方法没有 summary/param/returns，或注释只是复述方法名（如 `// saves the order`） | AGENT §2.3.2 |
| M7 | 关键代码缺业务注释 | 业务阈值、设备动作、报警映射、状态机分支、时序假设没有 `// 【...】--【人】/【日期】` 注释 | AGENT §2.3.3 |
| M8 | 注释签名格式错 | 注释没有按 `【内容】--【开发人】/【YYYY-MM-DD】` 格式写，或缺开发人或缺日期 | AGENT §2.3 |
| M9 | 魔法值 | 业务数字/字符串字面量直接出现在 if/赋值里，未提炼为 const/enum | AGENT §2.4.1 |
| M10 | async void | 异步方法签名是 `async void` 且不是事件处理器 | AGENT §2.4.1 |
| M11 | 方法参数 > 5 个 | 未用 Request/Options 对象封装 | AGENT §2.4.1 |
| M12 | 事件用匿名 lambda 订阅 | `foo.OnEvent += (s, e) => ...`，无法取消订阅 | AGENT §2.4.3 |
| M13 | 超长匿名 lambda | lambda 体内超过 5 行、有变量声明、有业务分支，未抽成具名方法 | AGENT §2.4.3 |
| M14 | 匿名类型跨方法传递 | 方法返回 `var`/匿名类型、或用 `new { ... }` 作为跨方法参数/返回值 | AGENT §2.4.3 |
| M15 | 过度防御 | 内部 private/internal 方法对参数重复做 null 校验；对不可能分支加 try-catch；嵌套 `a?.b?.c?.d` 应在前置卫语句处理 | AGENT §2.4.2 |
| M16 | 缺单元测试 | 新功能/新 public 方法没有对应测试用例，或测试只覆盖正常路径没覆盖异常/边界 | AGENT §2.7 |
| M17 | 测试命名不规范 | 测试方法名不符合 `MethodName_Scenario_ExpectedBehavior` 格式 | AGENT §2.7 |
| M18 | IDisposable 未 using | `new SqlConnection/FileStream/HttpClient` 等没包 using | AGENT §2.4.1 |
| M19 | 字符串比较未指定文化 | `str1 == str2`、`str1.Equals(str2)` 未用 `StringComparison.Ordinal*` | AGENT §2.4.1 |
| M20 | MR 描述不完整 | 缺"影响模块"、缺"自测结果"、缺"是否破坏公共接口"说明 | AGENT §3.3 |

### 2.3 Minor（m）—— 建议修复

| # | 检查项 | 判定标准 |
|---|---|---|
| m1 | 字符串拼接用 `+` 而非插值 `$"..."` | AGENT §2.4.1 |
| m2 | LINQ 查询被多次枚举（先 `.Count()` 再 `.First()`）未先 ToList | AGENT §2.4.1 |
| m3 | 集合初始化未指定已知容量 | `new List<T>(knownCount)` 可优化 |
| m4 | 存在性判断用 `.Count() > 0` 而非 `.Any()` | AGENT §2.4.1 |
| m5 | 变量声明远离使用位置 | AGENT §2.2 |
| m6 | 注释与代码不同步 | 注释说"返回 null"但代码已改成返回空集合 | AGENT §2.3 |
| m7 | 死代码 | 被注释掉的旧代码、没用的 private 方法 | AGENT §2.3.4 |
| m8 | 嵌套超过 3 层未用卫语句展开 | AGENT §2.4.1 |
| m9 | 缺少空行分隔逻辑块 | AGENT §2.2 |
| m10 | 测试数据重复构造，未用 Builder | AGENT §2.7 |

### 2.4 Nit（N）—— 提一下即可

- 变量名可读性（如 `data` vs `orderData`）
- 换行位置、空格细节
- 注释措辞优化
- using 排序

## 3. 多 Agent 协作场景专项检查

### 3.1 跨模块改动

- 本 MR 是否动了**不属于作者模块**的文件？
  - 是 → 看 MR 描述是否说明原因、是否 @ 了模块负责人；没说明升级为 **B10**。
- 是否有人"顺手重构"了无关代码？
  - 是 → 评论要求把无关改动拆到另一个 MR，不要混在业务改动里。

### 3.2 公共契约变更

- 看 diff 是否动了：
  - `I*Service` / `I*Repository` 接口签名
  - DTO / record 定义
  - 事件类 / 消息契约
  - 枚举值（新增枚举值要看下游 switch 是否穷尽）
- 如果动了，检查：
  - MR 描述里有没有"Breaking Change 清单"？
  - 有没有列出受影响的下游 Agent / 模块？
  - 是否考虑了向后兼容（重载、标记 `[Obsolete]`、过渡方案）？
- 缺清单 → **B7**。

### 3.3 交接完整性

- 如果这个 MR 是上一个 Agent 移交过来的，看交接文档是否包含 AGENT §1.2 的六段：已完成 / 当前状态 / 待办 / 已知坑 / 接口契约 / 未解决问题。
- 缺任何一段 → 在 MR 里要求补充，不阻塞代码本身但要在评论里指出。

### 3.4 模型风格痕迹

- 检查是否有某模型特有的啰嗦痕迹：
  - 大段解释"这段代码做了什么"的废话注释
  - 多余的 using、多余的访问修饰符
  - 过度设计的多层抽象（一个简单 if 搞出三个类）
  - 不一致的命名风格（突然冒出来一个 camelCase 的类名）
- 发现 → 打 **m**，要求清理。

## 4. 设备 / 工业控制专项检查

这类 MR 一旦有问题后果严重，**Reviewer 要格外敏感**：

- [ ] 是否动了 PLC 写入、点位地址、通信时序？
- [ ] 是否动了报警映射、联锁条件、急停逻辑？
- [ ] 是否动了状态机迁移、任务队列调度、批次流转？
- [ ] 是否动了仿真开关（是否会误把仿真模式带到生产）？
- [ ] 是否动了数据库连接、消息队列地址、API 端口？

**只要命中任意一条**：
- MR 描述里必须有"对现场设备/物理流程/安全的影响说明"。
- 没有说明 → 升级为 **B6**，要求作者补充并按 A 类流程走设计评审。
- 时序相关改动（如 `Thread.Sleep`、等待 PLC 响应）→ 必须看到 AGENT §2.3.3 要求的时序注释，没注释打 **M7**。

## 5. 流程与文档合规检查

按 MR 变更等级核对必备文档：

| 等级 | 必备产物 | 没看到怎么办 |
|---|---|---|
| A 类 | 需求说明 + 设计说明 + 测试计划 + 测试用例 + 测试记录 + 发布说明 + 上线配置清单 | 缺任何一份 → Major，要求补齐才能合并 |
| B 类 | 设计说明 + 联调记录（涉及设备）+ 测试计划 + 用例 + 记录 + 发布说明 | 缺 → Major |
| C 类 | 测试记录 + 发布说明 | 缺 → Minor，可合并后补 |
| D 类 | 无 | 放过 |

分支层面：
- feature/bugfix 分支合并到 development 后是否删除了？（这个在合并动作后检查）
- MR 到 development 之前，作者是否先 pull 了最新 development 本地解决冲突？（看 commit 历史里有没有 merge commit）

## 6. Reviewer 行为规范

### 6.1 应该做的

- **先看大方向再抠细节**：先通读整个 MR 搞清楚在干嘛，再逐行看。
- **指出问题时给替代方案**：不要只说"这里不对"，要说"建议改成 X"并给代码片段。
- **区分"问题"和"个人偏好"**：后者降级为 Nit。
- **对模糊处直接问**：看不懂作者为什么这么写，就问，不要假设作者错了——可能有你不知道的现场约束。
- **表扬好的实践**：发现特别清晰的注释、完整的测试，可以点出来，鼓励这种风格。
- **尊重作者**：评论用建议语气（"建议这里..."、"能否考虑..."），不用命令或嘲讽。

### 6.2 禁止做的

- ❌ **不要直接在 MR 里改代码 push**——提意见，让作者改。
- ❌ **不要把 Nit 级问题当作阻塞理由**——一堆 Nit 不应该 Request Changes。
- ❌ **不要为了凑评论数而挑刺**。
- ❌ **不要在不了解现场设备/工艺背景时，随意要求"简化"或"重构"联锁相关逻辑**——看不懂就问。
- ❌ **不要忽略 Blocker 级问题**：看到 B1-B10 任何一条，不要 Approve，不要"先合了再说"。
- ❌ **不要重复 reviewer 已经说过的话**——看线程历史再评论。
- ❌ **不要把自己的代码风格强加给作者**——一切以 chem-dev-rules（AGENT）规范为准，规范没写的不要管。

### 6.3 评论语气模板

- Blocker：`[B] 这里拼接了 SQL 字符串，有注入风险（AGENT §2.6）。建议改成参数化：` + 代码片段
- Major：`[M] public 方法 CreateOrderAsync 缺少 <returns> 和 <exception> 注释（AGENT §2.3.2），建议补上。`
- Minor：`[m] 这里字符串拼接建议用 $"" 插值（AGENT §2.4.1），可读性更好。`
- Nit：`[N] 变量名 data 有点泛，建议 orderData。`
- 疑问：`[?] 这里为什么要 Thread.Sleep(200)？是等 PLC 响应吗？如果是，建议加 AGENT §2.3.3 要求的时序注释。`

## 7. Review 结论判定矩阵

| 情况 | 结论 |
|---|---|
| 有任何 Blocker | **Request Changes** |
| 有 Major 但作者已在评论里解释并建了 TODO issue | 可 Approve，但要在总结里列 TODO |
| 只有 Minor / Nit | **Approve**（Comments 即可） |
| MR 描述里有疑问待作者回答 | **Comment**，不 Approve 也不 Request Changes，等作者回复 |
| 发现疑似设备/联锁/安全风险但不确定 | **Comment** 提问，并在总结"风险提示"里标注，要求作者和 Tech Lead 确认 |

---

## 8. Reviewer 自检清单（提交 Review 前自己过一遍）

- [ ] 我是否真的读了 MR 描述和全部 diff，而不是扫了一眼就开始评论？
- [ ] 每条评论都有：位置 + 级别 + 规范条款 + 建议吗？
- [ ] 我有没有把个人品味包装成 Major/Blocker？
- [ ] 我有没有遗漏 Blocker 检查（安全、设备、接口契约）？
- [ ] 结论是否与严重级别矩阵一致？
- [ ] 如果我 Approve 了，是否真的没有 Blocker？
