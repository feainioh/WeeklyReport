# SQLite 单机存储改造计划

## 1. 目标与范围

暂时停用 MySQL 业务存储和同步，应用运行时仅使用本机 SQLite。保留 MySQL 相关代码、迁移脚本与已有同步记录，但不在新版本的正常运行路径中调用它们。此计划只规划改造，尚未实现。

- 本机 SQLite 是唯一业务数据源，不代表异地备份或跨设备同步。
- SQLite 不存在时允许创建空库；已有库损坏、不可读写或迁移失败时明确报错，不回退 MySQL，也不覆盖原库。
- 保存工作记录、周报、Git 数据和导入备份仍须保持本地事务原子性。
- 新版本运行期间不连接 MySQL，包括自动任务、设置操作、初始化、镜像和手动同步。
- 暂不删除 MySQL 代码、依赖或表；未来重新启用需要另行设计和验证，不承诺简单切回即可同步。

## 2. 当前基础与影响

- [App.xaml.cs](../src/WeeklyReport.App/App.xaml.cs) 按 SQLite 状态选择本地或 MySQL 仓储；当前本地库不可用时存在回退 MySQL 的路径。
- [SqliteOperationQueue.cs](../src/WeeklyReport.Infrastructure/Persistence/Sqlite/SqliteOperationQueue.cs) 将 SQLite 业务变更和待同步操作组放在同一事务；单纯停止同步会持续积累待处理记录。
- [SqliteSyncCoordinator.cs](../src/WeeklyReport.Infrastructure/Persistence/Sqlite/SqliteSyncCoordinator.cs) 包含启动、周期和手动同步入口，隐藏按钮并不能阻止后台同步。
- [SqliteBackupStore.cs](../src/WeeklyReport.Infrastructure/Persistence/Sqlite/SqliteBackupStore.cs) 已支持 SQLite 业务备份，但现有 JSON/Excel 交换格式不包含全部本机绑定、队列及状态，不能视为完整工作库备份。
- 原[本地优先存储计划](./离线可用与本地优先存储计划.md)以 MySQL 同步为目标；实施本计划时应更新相关 ADR、说明和待办的适用状态，不把历史设计误认为当前产品承诺。

## 3. 数据保护与切换规则

### 3.1 升级前准备

- [ ] 区分已有 SQLite 工作库、只有 MySQL 数据、新安装三种情形；检查 SQLite 文件及元数据，不能仅凭缺少 SQLite 文件就认定是新用户。
- [ ] 对只有 MySQL 数据的用户，在升级到 SQLite-only 版本**之前**，使用现有版本提供的镜像或数据导出流程进行一次性迁移；检查结果和业务数据后再切换。迁移与新版本运行时零 MySQL 访问的约束互不冲突。
- [ ] 迁移失败、MySQL 不可用或数据来源无法判断时，不静默宣称数据已迁移。保留源库，提示恢复旧版或使用已有备份导入；是否创建空库须由用户明确选择。
- [ ] 如果 SQLite 与 MySQL 均有数据，不自动覆盖、合并或推断哪个更新。先分别备份，列出差异并由用户确定数据来源。
- [ ] 对现有 SQLite 的 `Pending`、`AwaitingConfirmation`、`Conflict`、`Failed` 等记录及身份元数据原样保留；不能自动删除、重放或标记为已同步。旧版在远端已提交但本地未确认的情况需要单独核对。

### 3.2 回滚与未来重新启用

- [ ] 切换前保留独立位置的可验证备份及旧版；切换后产生的新数据须先备份，不能靠直接切回旧版恢复同步。
- [ ] SQLite-only 期间不再生成同步操作组，因此旧队列和旧基线无法完整描述此后修改。未来恢复 MySQL 时必须先冻结写入、备份双方、比较数据并制定全量重建基线或明确的迁移方案，再决定是否处理历史队列；不得直接重启旧同步器。

## 4. 实施步骤

### 阶段 0：入口盘点与迁移保障

- [ ] 盘点依赖注入、数据库设置、备份、启动初始化、自动任务及同步入口，记录全部 MySQL 调用路径。
- [ ] 验证旧版镜像/导出覆盖的业务字段和 Git 本机绑定，补充切换指南；既有业务交换格式的缺失字段须明确告知。
- [ ] 定义可验证的完整工作库备份与恢复流程：使用 SQLite 在线备份 API 取得 WAL 一致快照；恢复前验证、备份当前库，恢复失败保留原库并明确报告。应用配置、凭据及提醒数据若不属于数据库，单独说明范围。

**完成条件：** 迁移前提、数据来源选择、失败与回滚路径明确，不修改或覆盖用户既有数据。

### 阶段 1：SQLite 唯一启动路由

- [ ] 初始化并迁移 SQLite，所有业务仓储、Git 存储及备份仓储统一注册 SQLite 实现。
- [ ] 实现新安装初始化，并区分既有库不可用、路径缺失和需要迁移的情况；禁止创建空库掩盖损坏或迁移失败。
- [ ] 移除本地异常时回退 MySQL 的路径；启动失败显示可理解的错误并记录不含敏感数据的诊断信息。

**完成条件：** 无 MySQL 配置即可启动和持久化；SQLite 故障不会连接 MySQL 或覆盖原文件。

### 阶段 2：停止同步并解耦事务

- [ ] 停止创建、启动和调用同步协调器及同步应用器，包括自动与手动入口。
- [ ] 从本地业务写事务中分离远端 outbox：工作记录、周报、Git 写入和备份导入仍保持原子性，但不新增 MySQL 待同步记录。
- [ ] 保留同步表与历史数据；调整状态提供者和业务消费者，避免历史冲突或暂停状态阻碍本地操作，也不把旧状态描述为正在同步。
- [ ] 针对写入中途失败验证整体回滚，并核对所有 SQLite 写入入口，避免只修改部分仓储。

**完成条件：** 业务操作成功后不新增远端队列；失败不产生部分本地业务数据；历史队列不变。

### 阶段 3：界面与文档

- [ ] 移除或停用 MySQL 配置、初始化、建立镜像、回退 MySQL 和立即同步入口，同时检查其后台调用已不可达。
- [ ] 存储状态显示本地 SQLite；说明数据保存在本机、不自动跨设备同步以及业务导出与完整备份的区别。
- [ ] 更新 README、相关存储/备份计划和 ADR：记录 SQLite-only 暂行决策、历史同步状态及重新启用前的基线要求。

**完成条件：** 用户无法从新版本界面或常规后台流程触发 MySQL 操作，文档和实际行为一致。

### 阶段 4：备份恢复与回归验证

- [ ] 按阶段 0 的流程实现或核验完整 SQLite 备份恢复；WAL 写入期间验证备份一致性，恢复后检查完整性、迁移和业务读写。
- [ ] 验证现有 JSON/Excel 业务导入导出及 Markdown 导出，保留预览、冲突策略与失败回滚语义。
- [ ] 覆盖新安装、既有 SQLite、只有 MySQL 数据、双份数据不一致、历史队列以及 SQLite 损坏、权限不足、迁移中断等场景。
- [ ] 验证业务、提醒、周报和 Git 工作流；构建并运行受影响测试，必要时运行完整解决方案测试。
- [ ] 通过可观测的网络/调用测试验证正常运行、设置操作和后台任务均不连接 MySQL；不要仅以隐藏按钮作为证明。

**完成条件：** 测试与构建结果记录清楚，迁移/备份/恢复和无 MySQL 访问的关键验收通过。

## 5. 验收清单

1. 全新安装无需 MySQL 即可创建 SQLite 并在重启后保留数据。
2. 既有 SQLite 的业务数据、Git 绑定与历史同步记录在升级后保留；普通本地写入及备份导入不新增待同步项。
3. 仅有 MySQL 数据时，升级前迁移可验证且失败不丢失源数据；无法确认数据来源时不静默以空库替代。
4. SQLite 不可用时明确报错，不回退、覆盖或连接 MySQL。
5. 所有正常 UI、手动操作和后台任务均不访问 MySQL。
6. SQLite 事务、业务交换、完整备份恢复及主要业务流程的成功、失败和重启场景通过验证。
7. 未来恢复同步的限制、备份范围和回滚要求均有明确说明。

## 6. 依赖和实施顺序

先完成数据保护与迁移规则，再进行启动路由、事务解耦和 UI 调整，最后实施完整备份恢复并开展端到端验收。完整备份恢复是本计划的验收内容，不应只以 JSON/Excel 导出替代。一次性 MySQL 迁移是升级前操作；新版本正常运行始终保持 SQLite-only。
