# WeeklyReport 全项目可维护性改造计划

> **范围：** 对 WeeklyReport 全部生产代码、测试、应用组合与相关文档进行分阶段维护性改进；SQLite 同步器只是其中一个重点，不是本计划的唯一范围。本计划是改造路线，不代表下列所有候选问题都已逐行确认或已开始实施。

**目标：** 在不改变现有产品行为和数据语义的前提下，降低重复实现与模块耦合，明确核心领域规则、应用用例、持久化适配器和 WPF 界面的边界；让关键行为能由自动化测试可靠保护。

### 剩余工作优先级

1. **P1 — 本机可继续：按范围完成剩余逐层审计。** 本轮已完成除 MySQL/SQLite 持久化实现外的 Domain/Application、配置与外部集成、WPF ViewModel/生命周期审计，并修复一项周报提醒导航失败状态问题。MySQL/SQLite 审计按用户要求不在本轮范围内；后续只有明确恢复该范围时再处理。
2. **P1 — 需隔离数据库：完成 MySQL 契约验收。** 准备独立 `weeklyreport_test_*` 数据库和本机凭据，运行 `scripts/test-mysql.ps1`；覆盖工作记录、周报、Git 项目/同步、备份、同步应用、首次镜像和并发变更，以及连接失败路径。当前 21 项 MySQL 用例尚未运行；记录隔离环境的实际通过/跳过/失败数前，不得宣称 MySQL 端到端通过。
3. **P1 — 需可交互桌面：完成 Windows 人工回归。** 验证启动/退出、托盘、设置、记录、Git、周报、导入导出、提醒及悬浮精灵。当前环境没有原生 WPF 交互工具，尚未执行。
4. **P2 — 收敛与关闭计划。** 完成可执行审计和环境验收后更新 README、本计划的阶段状态与测试基线，列明未解决或明确不纳入的功能；所有受影响测试、解决方案构建和差异检查均通过后，方可标记整体完成。

**未决范围决策：** SQLite-only 是用户正在考虑的架构方向，但尚未授权移除 MySQL；在单独确认迁移/数据保留方案前，继续保留 MySQL 实现与验收项，不以本轮审计代替架构切换。

**不属于本维护性计划修复项：** MySQL 远端基线/三方比较、更新/删除自动应用、备份导入同步和冲突解决是离线同步产品能力，仍未实现；除非另行扩大任务范围，不应与上述 MySQL 持久化缺陷修复混为一批。

**项目结构：**

- `WeeklyReport.Domain`：工时、日期、周报、Git 与提醒等领域规则。
- `WeeklyReport.Application`：业务用例、服务、端口/接口、调度策略与应用模型。
- `WeeklyReport.Infrastructure`：MySQL/SQLite 持久化、迁移、Git 命令、AI HTTP、备份编解码、配置与密钥保护。
- `WeeklyReport.App`：WPF 组合根、窗口、ViewModel、后台监控、系统托盘和精灵交互。
- `tests`：Domain/Application 单元测试、桌面测试、Infrastructure 集成与仓储契约测试。

**原则：**

1. 先确认重复、职责耦合或错误风险，再决定抽取；不以类的行数或“看起来整齐”作为重构理由。
2. 先建立行为测试，再重构；纯结构调整应保持输入/输出和持久化语义不变。
3. 不混合重构与产品需求、数据库协议变化或 UI 行为变更；若必须调整契约，列出所有调用方并单独验证。
4. MySQL 与 SQLite 实现遵循同一仓储契约，但不强行共享泄漏 provider 差异的底层实现。
5. 不引入新的通用框架或依赖，除非现有重复已由实际调用场景证明且方案明显更简单。
6. 保留未提交的既有工作；每阶段只触及对应范围，不通过全仓格式化/批量改名扩大差异。

## 4. Phase 2：持久化、备份和离线同步边界

**范围：** Infrastructure 的 MySQL/SQLite 仓储、迁移、备份编解码及同步组件。

- [ ] 对照仓储接口与 `WeeklyReportRepositoryContract`、`WorkEntryRepositoryContract`、Git/备份契约，补齐 MySQL/SQLite 一致性测试；provider 特定限制通过明确测试说明。
- [ ] 识别双 provider 中重复的业务决策、行映射、参数赋值和日期处理；只抽取行为完全一致且不会模糊事务责任的代码。
- [ ] 将 SQLite 操作组载荷、状态存储、同步编排、MySQL 事务应用等职责按真实边界梳理；不得仅拆分 `SqliteSyncApplier` 文件而不先解决载荷与事务契约。
- [ ] 优先解决不可变操作组快照：业务数据和操作组须同一 SQLite 事务提交；重试使用原操作载荷，不得从后续已变化的 SQLite 行重建旧操作。
- [ ] 按 ADR-03 补齐变更前基线、变更后值和幂等哈希的版本化协议；旧队列记录无法安全恢复时保留并显式转冲突/人工处理，不丢队列、不补造快照。
- [ ] 保持 MySQL 身份/协议校验、依赖与幂等回执、业务写入处于同一远端事务；基线无法证明安全时继续冲突，不自动覆盖。
- [ ] 评估备份校验、计划、JSON/Excel 编解码、文件访问的责任分布；保持导入事务原子性、文件大小/结构校验和敏感数据边界。
- [x] 移除同步器中不可达的 `backup_import` 派发分支和始终抛出异常的占位函数；当前备份导入仍在操作组校验阶段作为不支持操作保留为冲突。
- [x] 移除同步器待读取但未使用的 `PendingOperation.CreatedAtUtc` 字段映射；队列排序仍使用数据库中的 `created_at_utc`。
- [x] 将 MySQL 与 SQLite 备份覆盖时相同的更新时间推进策略集中到 `StorageDateRange.GetNextTimestamp`，由单一规则保持更新时间不倒退且至少推进一个微秒。

**验收：** 仓储契约在可用 provider 上通过；本地后续编辑不会改变已入队操作内容；多行事务失败整体回滚；远端并发冲突不会覆盖；备份输入/输出行为有测试保障。

## 8. 推荐执行顺序与首批切片

按以下顺序渐进实施，每个切片范围小、行为可验证：

1. 完成 Phase 0 审计和基线，确定 3–5 个高价值候选，不预先承诺大规模重写。
2. 优先处理 Phase 2 的操作组快照与同步安全门槛，因为它直接关系离线数据是否被错误覆盖。
3. 并行但分开处理已确认的 Domain/Application 重复规则和 Infrastructure 仓储一致性；每次只抽取一个业务规则或一个数据流。
4. 处理 App 装配与超大 UI/控件职责；先抽可测试边界，再调整文件布局和视觉代码。
5. 最后整理测试构造、日志/时间等横切机制与文档；不以“全仓统一风格”为理由改写稳定且无问题的代码。

**不在本计划中的事项：**

- 新产品功能、UI 改版或改变机器人/提醒/定时任务行为。
- 自动恢复所有离线冲突、跨设备同步或远程 MySQL 支持。
