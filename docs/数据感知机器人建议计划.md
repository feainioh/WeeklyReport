# 数据感知机器人建议开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans，按任务逐项实现。步骤使用复选框（`- [ ]`）跟踪。

**Goal:** 在现有悬浮精灵上增加“查看本周进展”和低频主动建议，建议基于有效业务数据与存储状态，有依据、可操作；第一版不增加 AI 请求，不自动写入任何业务数据。

**Architecture:** Application 定义 `IWeeklyProgressContextProvider` 与上下文/建议契约；App 先提供基于现有 MySQL 的实现，存储改造完成后由本地优先实现替换；建议策略是纯函数；精灵只负责气泡、动作和导航，不直接访问数据库。

**Tech Stack:** .NET 10、WPF、现有 CommunityToolkit.Mvvm/DI、SQLite 契约由存储计划提供、xUnit。

**Spec:** 本计划第 1–4 节；拆分来源见 [本地容灾与智能机器人扩展开发计划](./本地容灾与智能机器人扩展开发计划.md)（历史参考）。存储部分见 [离线可用与本地优先存储计划](./离线可用与本地优先存储计划.md)。

**Estimate:** 约 5–8 个工作日；可独立交付，不等待存储计划完成。该估算**不包含**第 11 节的后续 AI 扩展。

## 1. 目标、边界与命名

### 1.1 目标

1. 右键菜单增加“查看本周进展”；根据本周工作记录、周报保存状态、缺失工时、存储/同步状态给出建议。
2. 主动建议低频、可关闭、可跨重启记住每日一次；不把固定闲聊冒充状态感知。
3. 建议只导航到相关页面，不自动生成周报、不写库、不删除、不覆盖编辑器。
4. 默认信息卡片样式也能看到存储状态并进入状态详情；智能文案和动画只在精灵样式提供。
5. 存储改造完成后，机器人无需改 UI 即可从“MySQL 状态”切换到“本地优先/同步/冲突状态”。

### 1.2 命名与边界

- 本计划把“智能机器人”称为**数据感知建议**：第一版是规则化、可解释的上下文建议，不接 AI、不做通用聊天/语音/持续监听。
- 业务数据以当前有效数据源为准；在存储计划完成前是现有 MySQL，完成后是 SQLite 有效视图。
- 建议文案必须区分“查询结果为空”和“无法读取”；“已保存”不代表编辑器没有未保存修改。
- 工作时间口径沿用 `WeeklyReportDraftBuilder`：估算值不等于已确认值。

### 1.3 明确不做

- 第一版不新增 AI 请求、不发送业务内容给外部服务。后续 AI 扩展见第 11 节，需单独确认并拆分执行计划。
- 第一版不做通用聊天、语音、自动操作、自动生成周报、自动重算、自动导入。
- 不扩展远程 MySQL；不改变正式提醒的时间和系统通知规则。
- 不把机器人建议当作新的系统提醒；不额外补发提醒。

## 3. 数据契约

### 3.1 上下文

在 Application 层新增（文件名/命名可按实现调整，但字段语义固定）：

```csharp
public enum WeeklyStorageStatus
{
    MySqlHealthy,
    MySqlNotConfigured,
    MySqlUnavailable,
    LocalMode,
    SyncPending,
    Conflict,
    LocalUnreadable,
    Unknown
}

public sealed record WeeklyProgressContext(
    DateOnly WeekStart,
    int? ManualEntryCount,
    int? GitWorkItemCount,
    bool? HasSavedReport,
    int? UnknownHoursCount,
    WeeklyStorageStatus Storage,
    int PendingSyncCount,
    int ConflictCount,
    DateTimeOffset? LastSyncAtUtc,
    string? Error)
{
    public int? TotalWorkItemCount =>
        ManualEntryCount is null || GitWorkItemCount is null
            ? null
            : ManualEntryCount + GitWorkItemCount;

    public bool IsBusinessDataComplete =>
        ManualEntryCount is not null
        && GitWorkItemCount is not null
        && HasSavedReport is not null
        && UnknownHoursCount is not null;
}
```

- 任何一项查询失败时对应字段为 `null`，不得用 0 冒充“没有”；`Storage` 表示失败类别。
- `PendingSyncCount`/`ConflictCount`/`LastSyncAtUtc` 先在 MySQL 实现中为 0/null；存储计划完成后由本地优先实现填充。
- `Error` 只用于日志/调试，不直接展示给用户；用户看到的是策略生成的明确文案。

### 3.2 数据提供器

在 Application 层定义：

```csharp
public interface IWeeklyProgressContextProvider
{
    Task<WeeklyProgressContext> GetCurrentWeekAsync(bool forceRefresh = false);
    void Invalidate();
}
```

MySQL 实现（App/Services 或 Infrastructure）：

- 注入 `IWorkEntryRepository`、`IGitReportWorkItemSource`、`IWeeklyReportRepository`、`WeeklyReportDraftBuilder`、`TimeProvider`、`ILogger`。
- `WeekPeriod week = WeekPeriod.FromDate(DateOnly.FromDateTime(timeProvider.GetLocalNow().DateTime))`。
- 并行/顺序读取本周手工记录、Git 工作项、周报；用 `WeeklyReportDraftBuilder.Build` 得到 `UnknownHoursCount`（以及确认/估算工时，若需要）。
- 数据库未配置 → `MySqlNotConfigured`；连接/权限/超时等预期异常 → `MySqlUnavailable`；其他异常 → `Unknown`；日志记录异常类型，不回显原始错误。
- 缓存 30–60 秒；`Invalidate()` 由周报保存、工作记录变化、Git 同步、导入、切换数据源等事件调用；用户主动点击“查看本周进展”使用 `forceRefresh: true`。
- 查询不得阻塞 UI 线程；调用方在异步回调中更新气泡。
- 现有 `WeeklyReportStatusProvider` 可保留用于周报保存提醒；本计划的新提供器负责综合上下文，不改变提醒路径。

### 3.3 建议与动作

```csharp
public enum WeeklyAdviceKind
{
    StorageUnavailable,
    ConflictPending,
    SyncPending,
    UnknownHours,
    NoWorkItems,
    ReportNotSaved,
    ReportSavedCheck
}

public enum WeeklyAdviceAction
{
    WeeklyReport,
    WorkEntries,
    GitWorkItems,
    SyncStatus,
    StorageSettings,
    None
}

public sealed record WeeklyAdvice(
    WeeklyAdviceKind Kind,
    string Text,
    WeeklyAdviceAction Action,
    string ActionLabel);
```

- `Action` 只表示导航目标；`ActionLabel` 是按钮文字，例如“打开或生成本周周报”“打开工作记录”“查看同步状态”。
- 建议对象不包含数据库访问、命令或写入操作。

## 4. 建议策略与文案

### 4.1 优先级

建议按以下顺序生成；前一项成立时不再生成后一项：

1. **存储异常/未知**：`LocalUnreadable`、`MySqlNotConfigured`、`MySqlUnavailable`、`Unknown` → `StorageUnavailable`，动作 `StorageSettings`（MySQL）或 `StorageSettings`（本地存储），文案明确“暂时无法读取本周状态”。
2. **冲突**：`ConflictCount > 0` 或 `Storage == Conflict` → `ConflictPending`，动作 `SyncStatus`。
3. **待同步**：`PendingSyncCount > 0` 或 `Storage == SyncPending` → `SyncPending`，动作 `SyncStatus`。
4. **业务数据不完整**：`!IsBusinessDataComplete` → `StorageUnavailable`/通用未知，绝不推断“没有记录”或“未保存”。
5. **缺失工时**：`UnknownHoursCount > 0` → `UnknownHours`，动作 `GitWorkItems`。
6. **没有工作项**：`TotalWorkItemCount == 0` 且 `HasSavedReport == false` → `NoWorkItems`，动作 `WorkEntries`。
7. **有工作项、周报未保存**：`TotalWorkItemCount > 0` 且 `HasSavedReport == false` → `ReportNotSaved`，动作 `WeeklyReport`。
8. **周报已保存**：`HasSavedReport == true` → `ReportSavedCheck`，动作 `WeeklyReport`。

规则：

- “没有工作项”只在查询成功且总数为 0 时成立；不能把查询失败、空镜像或同步中当成没有。
- “已保存”只表示数据库中已有本周周报，不代表编辑器没有未保存修改；导航仍走现有确认逻辑。
- 工时数按 `WeeklyReportDraftBuilder` 的口径；不把估算值说成已确认值。
- 文案示例（最终可微调，但语义不变）：
  - “本周已有工作记录，周报还没保存，要整理一下吗？”
  - “本周周报已保存，可以打开检查是否需要补充。”
  - “本周有 2 项工作还没有可用工时，可以检查一下。”
  - “本周暂时没有工作记录，需要记一笔吗？”
  - “内容已保存在本机，还有 3 项变更等待同步。”
  - “有数据需要你确认，现有内容已保留在本机。”
  - “暂时无法读取本周状态，请检查存储设置。”
- 存储/冲突建议优先于业务建议；离线文案不得声称 MySQL 已更新。

### 4.2 主动建议

- 在现有空闲调度上增加低频主动建议：精灵可见、至少 5 分钟无交互、没有更高优先级气泡、未静音、非夜间、当天未建议过时才考虑。
- 每天最多一次，跨重启记住日期；新增 `LastAdviceDate` 持久化字段，与 `LastGreetingDate` 分开。
- 温和/活泼档默认开启，安静档默认关闭；设置页提供独立“数据建议”开关；预设切换恢复默认。
- 主动建议与闲聊互斥：同一轮空闲调度最多一条；数据查询异步，不阻塞 UI。
- 用户主动点击“查看本周进展”不受夜间/每日一次/临时静音限制，但仍需等待异步查询并遵守当前数据可用性；查询失败显示存储/未知建议。
- 正式提醒仍按既有时间和系统通知规则执行；本计划不新增提醒、不补发。冲突/存储异常建议可以覆盖闲聊，但不能覆盖正式提醒/未保存提醒气泡。

| 数据库未配置/不可用/读取失败 | 存储建议优先；不显示“没有记录/未保存”等业务断言。 |
| 存在待同步/冲突（未来本地优先） | 同步/冲突建议优先于业务建议；入口到同步状态/冲突页。 |
| 用户主动查看进展 | 不受夜间/每日一次/静音限制；查询失败显示存储建议。 |
| 主动建议 | 每天最多一次、跨重启记住；夜间/静音/气泡占用时不出；与闲聊互斥。 |
| 设置 | 安静默认关、温和/活泼默认开；开关持久化；切换预设恢复默认；不影响问候/提醒。 |
| 卡片样式 | 能显示存储状态并进入状态详情；不强制切换精灵样式。 |
| 导航 | 只切页/设日期/切分段；不写库、不生成周报、不覆盖未保存编辑。 |
| 正式提醒 | 不被建议/闲聊覆盖；不新增/不补发系统通知。 |

## 8. 风险与缓解

- **数据不完整导致误判**：所有业务字段可空；`IsBusinessDataComplete` 不成立时只给存储/未知建议。
- **MySQL 查询阻塞/慢**：异步 + 缓存 + 不阻塞 UI；失败降级为存储建议。
- **建议打扰**：每天一次 + 夜间/静音/气泡优先级 + 与闲聊互斥；安静档默认关。
- **导航副作用**：只做页面/日期/分段导航，禁止调用生成/保存/重算命令；保留未保存编辑确认。
- **存储计划状态差异**：先定义契约和假 context 测试；本地优先实现只映射状态，不改策略/UI。
- **“智能”预期过高**：文案和文档明确第一版是规则化数据建议，不接 AI。
- **卡片状态入口**：不阻塞卡片样式；MySQL 模式下只显示连接/配置状态。

## 9. 不纳入第一版

- 通用聊天、语音、持续监听、自动发送业务数据给 AI。AI 的后续可选路线见第 11 节，不属于第一版任务。
- 自动生成/保存周报、自动重算工时、自动导入 Git、自动解决冲突。
- 远程 MySQL、多设备协同、移动端。
- 新的系统通知/提醒渠道；正式提醒规则不变。

## 10. 与存储计划的关系

- 本计划只依赖 `IWeeklyProgressContextProvider`；第一阶段用现有 MySQL 实现，可独立交付并验收。
- 存储计划完成后新增本地优先实现，填入 `LocalMode/SyncPending/Conflict/LocalUnreadable` 与队列/冲突/最近同步字段；机器人 UI/策略不变。
- 两份计划共享“不自动写入、不覆盖未保存编辑、只注释不删除、测试全绿”的约束，但代码任务互不阻塞。

## 11. 后续 AI 扩展路线（非第一版）

> **本节不是第一版的执行任务，也不包含在上面的工期估算内。** 第一版仍是规则化数据建议；AI 是后续可选增强，必须在第一版验收通过、用户明确同意并单独拆分执行计划后再做。

### 11.1 目标与原则

- AI 只增强“解释、总结、提问”能力，不替代规则建议；离线、未配置 API Key、模型失败时，规则建议必须完整可用。
- **用户发起、发送前确认、应用前确认**；不做后台 AI 调用、不做自动重试风暴、不自动写入/保存/删除/重算/导入。
- AI 不直接访问数据库、文件系统、Shell 或任意工具；只接收应用构造的**最小化上下文**，只返回文本或结构化文本，由应用校验后展示。
- AI 输出必须标注“AI 生成”，不得把模型文本当作数据库事实；状态、计数、是否已保存等事实仍以本地有效视图为准。
- 复用现有 DeepSeek 能力，不新建第二套 AI 服务：现有 `IAiDraftService`、`AiDraftCoordinator`、`AiSettingsStore`、`AiReviewDialogs`、API Key DPAPI 保护、用户发送/应用确认流程。

### 11.2 可复用的现有能力

- [AiDraftCoordinator.cs](../src/WeeklyReport.App/Services/AiDraftCoordinator.cs)：加载设置、发送前确认、调用 `IAiDraftService`、应用前确认。
- [IAiDraftService.cs](../src/WeeklyReport.Application/IAiDraftService.cs)、`AiGenerationRequest`：已有模型、指令、内容、用户确认标志。
- [AiSettingsStore](../src/WeeklyReport.Infrastructure/Configuration/AiSettingsStore.cs) 与设置页 DeepSeek 配置：模型/API Key 已独立保存和保护。
- [WeeklyReportsViewModel](../src/WeeklyReport.App/ViewModels/WeeklyReportsViewModel.cs) 的 `GenerateWithAiAsync`：已有“生成总结 → 用户应用 → 手动保存”的流程，可作为 AI-2 的参考/复用点。
- 本计划的 `WeeklyProgressContext`、`WeeklyAdvice`、`WeeklyAdviceAction`：AI 只消费这些应用层数据，不直接查库。

- `SelectedWorkText`/`ExistingSummaryPreview` 必须由用户明确选择或确认后填入，并做长度截断；不是默认把全部工作内容发送出去。
- 上下文不得包含数据库密码、API Key、提醒去重状态、本机仓库路径、Windows 用户信息或同步队列内部细节。
- AI 输出只允许文本/受限 JSON；应用校验长度和字段，不执行模型给出的任何“操作指令”。
- 如果未来接入本地模型，应实现同一接口/同一套确认流程，不改变机器人 UI 和策略。

### 11.4 AI 阶段建议

**AI-1：解释当前建议（只读，最低风险）**

- 用户右键“让 AI 解释”或建议气泡中的“AI 解释”按钮触发。
- 发送前展示：模型、目标地址、建议文案、上下文摘要和将被发送的工作内容；用户确认后才请求。
- AI 返回对建议的解释/下一步建议；只读展示，不应用、不写库。
- 失败/超时/未配置 Key 时关闭 AI 结果并保留规则建议，不弹错误轰炸。

**AI-2：生成本周进展摘要/下周计划草稿**

- 复用现有 DeepSeek 生成流程：发送前确认、结果预览、用户确认后应用到周报编辑器，仍由用户手动保存。
- 不自动保存、不自动覆盖已有编辑器内容；应用前展示差异或明确的“替换/插入”选择。
- 与现有周报编辑器“DeepSeek 生成总结”不要重复；优先复用同一套服务，避免两个入口行为不一致。

**AI-3：本周数据问答（只读）**

- 用户用自然语言问“本周做了什么/还差什么/哪里没填工时”等问题。
- 只基于 `WeeklyAiContext` 回答；上下文不足时明确说“只能看到这些信息”，不编造。
- 不做通用聊天，不保留长期对话，不后台监听；结果可关闭/清除。

**AI-4：受控操作建议（更后）**

- AI 可以建议“打开周报页并预填某段文字”，但必须展示将要执行的操作和差异，用户确认后才执行。
- 仍然禁止自动保存、自动删除、自动重算、自动导入；任何写入都要走现有确认/事务/并发保护。

**AI-5：本地模型/离线 AI（可选）**

- 仅在隐私、模型体积、性能和发布依赖都验证后评估；第一版不承诺。
- 与云端 AI 使用同一接口和确认流程；不得因为“本地”就绕过用户确认或数据最小化。

### 11.5 UI、设置与隐私

- 设置页新增独立的“AI 建议”开关，默认关闭；与第一版“数据建议”开关分开，AI 关闭不影响规则建议。
- 复用现有 DeepSeek 模型/API Key 设置；发送前显示费用/隐私提示，明确会发送哪些内容。
- AI 结果使用对话框/预览窗口展示（气泡宽度有限，只用于“AI 结果已准备好”的提示），并标注“AI 生成”。
- 默认不后台预生成、不缓存模型输出到业务数据库；如需缓存，必须有明确清理/隐私策略。
- 用户可取消请求、关闭 AI、拒绝应用结果；失败不自动重试、不影响规则建议和正式提醒。
- 日志不得记录完整 prompt、周报正文、API Key 或响应正文；只记录异常类型/耗时等元数据。

### 11.6 安全与防滥用

- **Prompt injection：** 工作内容是不可信数据；prompt 中明确分隔数据与指令，禁止模型执行数据中的指令；应用不把模型输出当命令执行。
- **数据最小化：** 只发送本周计数/状态和用户选中的文本；不发送密码、API Key、提醒状态、本机路径、完整历史。
- **无工具权限：** AI 不获得数据库、文件、网络（除自身 API）、Shell 或 UI 自动化能力；输出只作为文本/受校验结构化数据。
- **成本与配额：** 用户发起 + 发送前确认 + 取消 + 超时；不做后台批量调用；记录费用提示，不自动重试。
- **输出校验：** 长度、编码、空响应、拒绝/错误响应；失败回退规则建议；不把未知/失败当事实。
- **模型/服务变更：** 继续使用现有 DeepSeek 配置；更换模型或服务需另行评估隐私、费用和输出质量。

### 11.7 AI 扩展的测试与验收

- 未明确触发时 **零 AI 请求**；发送前确认弹窗展示模型、地址、上下文摘要和将发送文本。
- 取消/超时/API 失败/未配置 Key：规则建议仍可用，不产生业务写入，不弹重复错误。
- 应用 AI 结果前必须再次确认；拒绝后编辑器/数据库不变；不自动保存。
- 上下文不包含密码/API Key/提醒状态/本机路径；工作内容只在用户选择/确认后发送。
- Prompt injection 用例（工作内容包含“忽略以上指令/执行某操作”）只能被当作数据，不产生工具调用或业务操作。
- 使用假 `IAiDraftService` 做单元测试，不调用真实 API；真实 DeepSeek 只做手动/隔离验证。
- 设置：AI 开关默认关闭；关闭后无请求；不影响规则建议、问候、提醒和正式通知。
- 手动验收：AI 结果标注“AI 生成”；费用/隐私提示可见；失败回退规则建议；AI 结果不会绕过未保存编辑保护。

### 11.8 与第一版/存储计划的关系

- 第 11 节不属于当前 Task 1–5，也不包含在 5–8 天估算内；当前版本先交付规则化数据建议。
- AI 依赖第一版的 `WeeklyProgressContext`/`WeeklyAdvice`，以及存储计划提供的存储/同步状态；不直接访问 SQLite/MySQL。
- AI 扩展需要单独确认需求、隐私边界和费用，再拆分为新的执行计划；在此之前不写 AI 代码、不新增 AI 依赖。
