# 离线可用与本地优先存储开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans，按阶段逐项实现。步骤使用复选框（`- [ ]`）跟踪。

**Goal:** 在现有 Windows 桌面周报工具上增加 SQLite 本地工作副本，使本机 MySQL 不可用时仍能读写全部业务数据；MySQL 恢复后自动应用可安全合并的变更，冲突保留双方并由用户处理。

**Architecture:** SQLite 作为本地优先的工作副本和待同步队列；Application 增加存储状态、操作组、冲突与同步协调接口；Infrastructure 增加 SQLite 完整仓储、MySQL 同步协议和幂等应用；App 负责启用/初始化/状态/冲突界面。

**Tech Stack:** .NET 10、WPF、SQLite（Phase 0 选型）、MySQL、SqlSugar 或等价持久化组件、xUnit。

**Spec:** 本计划第 1 节与第 3 节；拆分来源见 [本地容灾与智能机器人扩展开发计划](./本地容灾与智能机器人扩展开发计划.md)（已保留为历史参考）。机器人部分独立见 [数据感知机器人建议计划](./数据感知机器人建议计划.md)。

**Estimate:** Phase 0 约 3–5 个工作日；Phase 1 约 7–10 个工作日；Phase 2 约 15–25 个工作日；Phase 3 约 3–5 个工作日。按一名熟悉本项目的开发者估算，Phase 0 结论可能改变后续范围。

## 1. 目标、命名与边界

### 1.1 目标

1. MySQL 不可用时，工作记录、Git 项目与本机绑定、Git 工作项/提交去重、工时、周报、JSON/Excel/Markdown 导入导出仍可完整工作。
2. 本地保存成功不等于 MySQL 已保存；界面必须区分“已保存到本机”和“已同步到 MySQL”。
3. MySQL 恢复后自动同步能够证明安全的变更；不能证明安全时保留双方并进入冲突处理，不按时间戳或“最后写入者获胜”覆盖。
4. 首次启用、数据库切换、身份不匹配、迁移失败、SQLite 损坏等异常必须明确暴露，不能伪装成正常同步。

### 1.2 命名

本期把原“本地容灾”改称**离线可用与本地优先存储**。SQLite 与 MySQL 在同一台机器、同一磁盘上，**不构成异地容灾或独立备份**；真正的数据保护仍由用户导出的独立位置备份和 MySQL 自身备份负责。README/设置页必须使用这一措辞。

### 1.3 明确不做

- 不支持远程 MySQL、多设备自动发现、多人协同或端到端加密。
- 不把 SQLite 宣传为异地备份；不承诺磁盘损坏、勒索软件下的零丢失。
- 不自动安装/升级 MySQL，不静默覆盖生产数据。
- 不增加 AI 请求；机器人建议见独立计划。

### 1.4 已确认的产品选择

- 数据库范围仍为**现有本机 MySQL**；“远程数据库不可用”按现有 MySQL 不可用处理。
- 同步采取**自动同步无冲突变更，有冲突时提示用户**；不能安全判断时按冲突或待处理处理。
- 离线范围覆盖全部业务表、Git 本机绑定/提交去重/删除状态、工时与周报，以及现有导入导出。
- 保持现有数据库密码、API Key、提醒状态独立受保护，不写入业务 SQLite 或同步队列。
- 现有 JSON/Excel 导出语义保持不变；完整本机备份是新增能力。

## 3. Phase 0：选型、Spike 与决策门禁（先做，限时）

Phase 0 的目标不是写产品代码，而是用最小可丢弃 spike 证实或推翻本计划的核心假设。**时间盒 5 个工作日**；spike 代码不合并，结论写入 ADR 和本计划。

### 3.1 必须回答的问题

1. **主数据源和同步方向。** 默认按已确认选择：SQLite 本地优先 + 双向安全同步（方案 A1）。如果 spike 证明成本/风险不可接受，必须在以下备选中明确选择，不得含糊：
   - A2：SQLite 主库 + 单向镜像/导出到 MySQL（外部修改 MySQL 时要求人工导入/重建，不做自动双向合并）。
   - A3：MySQL 主库 + SQLite 只读缓存 + 离线写队列（离线期间只保证有限读取和排队写入）。
2. **SQLite 驱动。** SqlSugar SQLite 是否支持本计划需要的事务、WAL、锁、类型和在线备份；若不能，改用 `Microsoft.Data.Sqlite` 或等价组件，并验证 `win-x64` 自包含发布的原生依赖。
3. **语义一致性。** 逐个核对：GUID/主键、日期与 UTC 精度、字符串长度与排序规则、布尔/整数/工时数值、外键、唯一键、软删除、事务隔离、空值语义。不得假定 MySQL SQL 可直接用于 SQLite。
4. **同步最小闭环。** 用一个真实业务事务组（例如手工记录保存 + 周报更新）验证：SQLite 同事务入队、MySQL 基线比较 + 业务写入 + 幂等回执同事务、响应丢失后同 ID 重试、冲突检测。
5. **故障与测试能力。** 能否用可控故障注入验证“MySQL 已提交但响应丢失”“本地确认前崩溃”“Git 多行事务中途失败”；如果测试不可行，Phase 2 不启动。

### 3.2 Phase 0 任务

- [ ] 盘点所有业务读写入口：工作记录、Git 项目/同步/工作项/重算、周报、备份导入导出、状态查询、启动迁移；形成入口清单和未保存编辑保护清单。
- [ ] 用临时 spike 工程验证 SQLite 驱动与真实 schema 的兼容性；记录类型、UTC、排序规则、外键、唯一键、事务和自包含发布结果。
- [ ] 用最小操作组验证 MySQL 幂等回执、基线比较、事务隔离、死锁/锁等待重试和响应丢失处理。
- [ ] 用临时 spike 或测试替身验证崩溃/故障注入方法，形成可重复的测试方案。
- [ ] 产出 ADR：
  - ADR-01 主数据源/同步方向（默认 A1；若改 A2/A3，重写 Phase 1–2 的相应部分）；
  - ADR-02 SQLite 驱动与发布依赖；
  - ADR-03 数据模型：镜像表、操作组、基线、冲突、数据库身份、协议版本；
  - ADR-04 冲突界面与恢复入口；
  - ADR-05 时间/版本/迁移规则。
- [ ] 产出 ERD、状态机、故障状态表和接口清单（Application 层）。
- [ ] **Go/No-Go：** 以上关键假设任一无法证明，暂停 Phase 2，选择 A2/A3 或停止本计划；不能带着未验证的假设进入双向同步实现。

**验收：** ADR、ERD、入口清单、故障状态表、可重复的 spike 结论；明确记录的 Go/No-Go。阶段产出不合并到正式代码。

**建议决策记录：** 默认保留 A1；如果 MySQL 仅用于外部报表/备份、且允许人工处理外部修改，A2 能显著降低复杂度；如果只需“MySQL 短暂不可用时还能记账”，A3 可能已经够用。

## 4. 数据模型与同步协议（Phase 0 定稿，以下为默认方案）

### 4.1 本地业务库

- SQLite 文件位于当前用户 `%LOCALAPPDATA%\WeeklyReport`，与现有配置及日志同目录但独立文件；文件与队列含明文业务数据，必须在文档中说明。
- 业务镜像表与 MySQL 业务表一一对应，使用相同的业务主键（现有 GUID）和自然键/唯一约束；必要时增加 `revision`/`updated_at` 镜像列。
- 独立元数据表至少包含：
  - `local_meta`：SQLite schema 版本、同步协议版本、镜像身份、最近完整镜像时间、存储状态、最近成功同步时间；
  - `sync_operation`：操作组 ID、业务事务类型、变更内容、原始基线、依赖组、状态（待同步/同步中/结果待确认/冲突/已同步/失败）、创建/尝试时间、内容哈希；
  - `sync_conflict`：操作组、对象、本地版本、MySQL 版本、基线、冲突原因、用户处理状态；
  - 可选 `sync_queue_stats` 或从 `sync_operation` 聚合，避免独立状态不一致。
- MySQL 侧新增同步元数据/回执表（具体名称 Phase 0 定）：
  - 数据库身份与协议版本；
  - `sync_receipt(op_group_id PK, content_hash, applied_at, result)`；业务写入与回执必须同一 InnoDB 事务提交。
- 操作组的内容是**语义化变更集合**（表、行主键、自然键、操作类型、变更前基线、变更后值），不是原始 SQL；避免 SQL 方言耦合，并便于比较/冲突展示。
- 同一业务事务的多表变更（周报 + 工时引用、Git 项目 + 工作项 + 提交链接 + 工时）属于同一操作组；依赖组完成后才应用后续组。
- 队列保留/压缩策略：已同步组保留一段时间用于排查，之后可按策略归档/清理；未同步/冲突组永不静默删除；长期离线时设置上限并提示用户导出，不丢弃业务意图。

### 4.2 本地事务与版本

- 业务读取统一从“当前有效视图”读取；启用本地优先后，业务写入在同一个 SQLite 事务中完成业务表更新、删除意图和 `sync_operation` 入队；提交成功才提示“已保存到本机”。
- 手工记录/周报的物理删除必须转成可同步的删除意图和基线；Git 工作项继续使用软删除/提交去重语义。
- 连续编辑同一对象时保留正确的依赖和基线；不能因为队列压缩丢失已确认工时、删除或中间引用。
- 跨仓储读取/写入不得绕过统一数据访问入口；盘点清单中的每个入口都要接入 SQLite 路径。
- 后台同步与编辑并发时使用单一同步协调器和清晰事务边界；后台刷新不得覆盖未保存编辑器；保留现有 `UpdatedAtUtc` 乐观并发检查。

### 4.3 同步与冲突

1. 同步前核对数据库身份、协议版本、依赖和基线；读取目标行与自然键比较。
2. MySQL 事务内完成基线比较、必要的行/键范围锁或等价并发控制、业务写入和幂等回执；不能只在事务外先查再写。
3. 同一操作组 ID 重试：回执存在且内容哈希一致 → 返回已应用结果；哈希不一致 → 停止并报错。业务失败时回执不能单独提交。
4. 提交响应丢失视为“结果待确认”，重连后用同一 ID 查询/重试；不得生成新 ID 盲目重复。
5. MySQL 确认后，在 SQLite 事务中更新基线、操作状态和最近同步时间；任意步骤崩溃重启后可安全恢复。
6. 周期性刷新 MySQL 变化并进行三方比较；只有无本地待处理变更的对象才自动更新；双方变化进入冲突。无法证明删除范围时不得把缺失行当安全删除。
7. 冲突解决再次比较目标；预览后目标变化要重新预览；关联事务组不能拆成破坏外键/唯一约束的半成功状态。
8. 认证失败、权限不足、迁移错误、数据校验失败显示明确原因；断线用有上限退避，不无限重试，不当成普通断线。

### 4.4 初始化、身份与恢复

- 首次启用先检查连接、版本、权限和目标库；用户确认后执行版本化迁移；MySQL DDL 可能隐式提交，不能承诺完整回滚。
- MySQL 数据库身份持久记录；SQLite 记录绑定身份和连接配置标识。配置变化、数据库替换/恢复、身份不匹配、协议不兼容时暂停同步并要求用户确认；克隆数据库也可能保留身份，恢复后需显式核对。
- 首次在线初始化从 MySQL 取一致性快照（项目绑定、工作项、提交链接、周报、删除状态、基线），写入临时 SQLite 事务，校验后标记镜像可用；不得用 `BackupDocument` 替代完整镜像。
- 首次启动 MySQL 不可用时提示“尚无可用镜像”；允许用户建立空本地工作区继续录入，但标记“无已验证基线”，恢复后先核对身份和数据，无法证明安全的合并进入冲突，不把空库解释成 MySQL 为空。
- 不用新快照静默覆盖未同步修改；重新绑定/重建镜像前展示待同步与冲突数量并允许导出；取消/失败保留原文件和队列。
- 完整本机备份使用 SQLite 在线备份 API 或等价一致性机制，包含业务表、基线、队列和状态；WAL 模式下禁止只复制正在使用的主文件。
- 恢复完整本机备份前预览时间、身份、待同步/冲突数量并确认；恢复后暂停同步、校验身份和基线，不能把旧队列重放到其他/已回滚数据库。
- 禁用本地优先/回退 MySQL-only 前必须处理完或导出待同步/冲突；提供明确路径，不能直接丢弃 SQLite。

### 4.5 状态模型

至少区分并同时展示关键原因和数量：

| 状态 | 含义 |
| --- | --- |
| 已同步 | 本地与 MySQL 一致，队列为空 |
| 待同步 | 本地已保存，等待同步 |
| 同步中 | 正在提交某个操作组 |
| 结果待确认 | 请求结果不确定，等待同 ID 查询/重试 |
| 冲突待处理 | 双方版本保留，等待用户 |
| 连接/配置异常 | MySQL 不可达、身份/协议/迁移/权限问题 |
| 本地存储异常 | SQLite 不可写/损坏/空间不足/迁移失败 |

保存/同步文案不得把“本地保存”说成“MySQL 已保存”；离线时不声称 MySQL 已更新。

## 6. 分阶段任务

### Phase 1：SQLite 完整业务能力

- [ ] 建立 SQLite schema/迁移/连接管理；实现全部业务仓储；与 MySQL 仓储共享契约测试。
- [ ] 保持项目本机绑定、Git 提交去重/软删除/修订号、工时估算与确认、周报周唯一和编辑保护。
- [ ] 实现本地事务 + `sync_operation` 入队；业务操作与队列同事务提交。
- [ ] 实现首次镜像、无基线空工作区、SQLite 错误状态、状态查询接口。
- [ ] JSON/Excel/Markdown 导出和 JSON/Excel 导入切到当前有效数据；实现 SQLite 在线备份/恢复预览。
- [ ] 盘点清单中的每个读写入口都有 SQLite 路径；未保存编辑/忙碌保护不回归。
- [ ] 测试：仓储契约、迁移、类型/UTC/排序规则、外键/唯一键、事务回滚、SQLite 不可写/损坏/空间不足、Git 事务组、备份恢复。

**验收：** 隔离测试中停止 MySQL 后，完整工作流可保存、重启后读取、预览并确认 Git 同步和备份导入；SQLite 不可写时不显示成功；现有导入冲突和文件格式约定不变；现有测试全绿。

### Phase 2：自动同步、冲突与恢复

- [ ] 建立 MySQL 同步元数据/回执表、身份/协议版本和迁移；与现有业务迁移协调。
- [ ] 实现操作组应用：身份/协议/依赖检查、事务内基线比较、幂等回执、提交响应丢失、崩溃恢复、死锁/锁等待超时重试。
- [ ] 实现后台同步协调器：生命周期、退避、取消、启动/唤醒/手动立即同步、状态通知。
- [ ] 实现 MySQL → 本地安全刷新和三方比较；生成冲突记录，不自动覆盖。

## 7. 必测场景

| 场景 | 必须满足 |
| --- | --- |
| 首次启用、MySQL 正常 | 镜像完整一致，含 Git 绑定/提交去重/删除状态；校验后才标记已初始化。 |
| 首次启动 MySQL 不可用 | 提示无有效镜像；空工作区须用户选择；恢复后缺基线内容不静默覆盖。 |
| 停止 MySQL 后新增/修改/删除 | 保存到 SQLite 并留下待同步意图；重启后数据和状态仍在。 |
| MySQL 事务提交前中断 | 本地修改保留；恢复后同操作组安全重试。 |
| MySQL 已提交但响应丢失 | 同 ID 重试识别已应用，不重复创建。 |
| MySQL 提交后、本地确认前崩溃 | 重启识别已提交并修复本地状态，不误报失败/重复。 |
| 双方修改同一记录 | 两版本保留为冲突；预览后 MySQL 再变要求重新预览。 |
| 双方新增同周周报/同项目同日 Git 项 | 按自然键冲突，不违反唯一约束。 |
| 一方删除、一方修改 | 删除意图与修改都保留；Git 删除项不被静默重建。 |
| Git 多行事务中途失败 | 项目/工作项/提交链接/工时无部分提交；重试不重复。 |
| 认证/权限/协议不匹配 | 本地数据保留，显示具体异常，不当成功。 |
| 数据库切换/替换/备份恢复 | 暂停同步并核对身份/基线，不向错误目标重放。 |
| SQLite 满盘/损坏/不可写 | 不显示保存成功，不清空文件，提供错误和恢复提示。 |
| SQLite 在线备份/恢复 | 业务/绑定/基线/队列一致；恢复后暂停并校验。 |
| 队列长期增长/压缩 | 不丢失未同步/冲突意图；达到上限提示导出。 |
| 禁用本地优先/回退 | 待同步/冲突处理或导出后才能回退；不丢数据。 |
| 应用离线升级 | SQLite schema、MySQL schema、同步协议版本可协调；不误同步。 |
| SQLite 锁/WAL busy/多 Windows 用户 | 有明确错误/等待策略；不写坏文件。 |

## 8. 风险与缓解

- **双写同步是最大风险**：优先 Phase 0 spike；默认 A1，无法证明安全时退 A2/A3；不带着假设进入 Phase 2。
- **SQLite/MySQL 语义差异**：合同测试逐项验证；不共享原始 SQL。
- **崩溃/响应丢失**：同操作组 ID + 回执 + 基线；故障注入测试。
- **外部修改/数据库替换**：身份/协议/基线校验；不安全即冲突/暂停。
- **SQLite 原生依赖/发布**：Phase 0 验证自包含 win-x64；不通过则换驱动或停止。
- **明文数据/磁盘损坏**：文档说明，不宣称为备份；继续独立位置备份。
- **范围过大**：Phase 0 Go/No-Go、时间盒、A2/A3 回退；机器人计划独立交付，不阻塞。
- **测试成本**：Phase 0 先验证故障注入能力；测试框架是 Phase 2 的前置条件。

## 9. 不纳入第一版

- 远程 MySQL、多设备自动发现、多客户端协同、通用 CRDT。
- SQLite 文件加密、异地备份、磁盘/勒索软件零丢失承诺。
- 自动安装/升级 MySQL、静默覆盖生产库。
- 机器人建议、AI 请求、语音/聊天（见独立计划）。

## 10. 与机器人计划的关系

- 本计划提供 `StorageStatus`、待同步数量、冲突数量、最近同步时间等状态契约；机器人计划只消费这些接口，不直接访问数据库。
- 机器人计划第一阶段可以使用现有 MySQL 实现自己的数据提供器，不等待本计划完成；本计划完成后替换为本地优先实现。
- 两份计划共享“只注释不删除”和测试全绿约束，但代码任务互不阻塞。
